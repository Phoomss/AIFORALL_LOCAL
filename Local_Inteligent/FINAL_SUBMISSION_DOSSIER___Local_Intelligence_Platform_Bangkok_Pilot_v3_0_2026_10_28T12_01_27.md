### 2.1 Core Statement — หัวใจของโครงการ

> **"เปลี่ยนคำเตือนสภาพอากาศและจราจรที่เป็นข้อมูลตั้งรับ (Passive Warnings) ให้กลายเป็นแผนปฏิบัติการเชิงรุกระดับหน้างาน (Actionable Hyper-local Decisions) ผ่านกรอบคิด Risk → Impact → Action ที่ขับเคลื่อนด้วย AI สมองกลเดียว ส่งมอบ 3 ประสบการณ์ที่เข้าใจบริบทเฉพาะพื้นที่"**

ระบบ AI ทั่วไปหยุดอยู่แค่บอกว่า *"พรุ่งนี้ฝนตกหนัก 85 มม."* แต่ **Local Intelligence Platform** ไปไกลกว่านั้น — มันบอกร้านขายยาเจริญโอสถบนถนนเยาวราชว่า *"ย้ายสมุนไพรลิ้นชักล่าง 2 แถว + รังนกแห้งขึ้นชั้น 3 ก่อน 10:00 น. เพื่อลดความเสียหาย ฿35,000"* — นี่คือสิ่งที่เราเรียกว่า **Hyper-local Actionable Intelligence**

### 2.2 Track Fusion Rationale — ทำไมต้องรวม 3 Track ด้วย 3 Copilots

แพลตฟอร์มนี้ไม่ได้ "รวม Track เพื่อให้ครบ" แต่รวมเพราะ **ปัญหาทั้ง 3 ด้านมีรากฐานข้อมูลเดียวกัน** และ **การแก้ปัญหาด้านหนึ่งส่งผลดีต่ออีกด้านโดยอัตโนมัติ:**

```
    ┌─────────────────────────────────────────────────────────────────┐
    │              UNIFIED AI INTELLIGENCE LAYER                      │
    │  Weather + Traffic + Flood + Tourism + SME + Community Data     │
    │  Predict → Analyze → Recommend → Explain                       │
    └──────┬──────────────────┬──────────────────┬────────────────────┘
           │                  │                  │
    ┌──────▼──────┐   ┌──────▼──────┐   ┌──────▼──────┐
    │ Track 6      │   │ Track 5      │   │ Track 2      │
    │ RESILIENCE   │──▶│ MOBILITY     │──▶│ SME ECONOMY  │
    │ LocalShield  │   │ SafeRoute    │   │ LocalFlow    │
    │ Business     │   │ Mobility     │   │ Tourism      │
    │ Copilot      │   │ Copilot      │   │ Copilot      │
    └──────────────┘   └──────────────┘   └──────────────┘
    "ร้านต้องทำอะไร?"   "ไปทางไหนปลอดภัย?"  "เที่ยวไหนคุ้ม?"
```

**วงจรเชื่อมโยง (Synergy Loop):**

1. **Track 6 → Track 5:** ข้อมูลน้ำท่วมและความเสี่ยงชุมชน (LocalShield) ถูกส่งต่อเป็น Input ให้ SafeRoute คำนวณเส้นทางปลอดภัย
2. **Track 5 → Track 2:** เส้นทางที่ SafeRoute แนะนำจะผ่านร้านค้า SME ชุมชนที่ LocalFlow คัดเลือก ทำให้เม็ดเงินท่องเที่ยวกระจายสู่เศรษฐกิจฐานราก
3. **Track 2 → Track 6:** SME ที่ได้รับประโยชน์จาก LocalFlow จะส่งรายงานสภาพพื้นที่กลับเข้าระบบ (Community Reports) สร้าง Crowdsourced Resilience Network

### เกณฑ์ที่ 5: ความยั่งยืนและความเป็นไปได้เชิงธุรกิจ (Sustainability & Viability) — คะแนนเต็ม 10

#### 5.1 Hybrid Revenue Model — 3 แหล่งรายได้

**แหล่งที่ 1: B2B/SME Freemium (รายได้จากผู้ประกอบการ)**
- **Free Tier:** แจ้งเตือนความเสี่ยง Basic + ลงทะเบียนรับนักท่องเที่ยวจาก LocalFlow
- **Premium Tier (฿299-999/เดือน):** วิเคราะห์ธุรกิจเชิงลึก, แผนปฏิบัติการอัตโนมัติแบบเฉพาะร้าน, Priority Ranking ใน LocalFlow, Dashboard Analytics
- **Revenue Sharing:** คอมมิชชั่น 5-10% จากการจอง Workshop/คูปองผ่าน LocalFlow

**แหล่งที่ 2: B2G/Smart City (รายได้จากหน่วยงานรัฐ)**
- สัญญาบริการข้อมูลกับเทศบาล/อปท. สำหรับบริหารจัดการน้ำท่วม ความแออัด และกระจายเศรษฐกิจชุมชน
- Dashboard สำหรับการท่องเที่ยวแห่งประเทศไทย (ททท.) ติดตามการกระจายตัวนักท่องเที่ยวและรายได้สู่ชุมชน

**แหล่งที่ 3: B2B2C/Logistics API (รายได้จากแพลตฟอร์มขนส่ง)**
- SafeRoute API สำหรับ Grab, LINE Man, Lalamove — ลดอัตราอุบัติเหตุและความล่าช้าในช่วงน้ำท่วม
- ค่าบริการ API Call-based pricing (฿0.50-2.00/request)

#### 5.2 Community Incentive Loop — วงจรเศรษฐกิจหมุนเวียน

```
ประชาชน/ไรเดอร์ ──[ส่งรายงานสภาพถนน/น้ำท่วม]──▶ ระบบ AI (ข้อมูลดีขึ้น)
        ▲                                                        │
        │                                                        ▼
   [แลกแต้มเป็นส่วนลด]                              [SafeRoute/LocalFlow แม่นยำขึ้น]
        │                                                        │
        └──── SME ชุมชน ◀──[นักท่องเที่ยว + ลูกค้าเพิ่ม]────────┘
```

- **ผู้รายงาน** ได้แต้มสะสม → แลกส่วนลดร้านค้า SME ในเครือข่าย
- **SME** ได้ลูกค้าเพิ่ม → ยินดีให้ส่วนลดเป็นแรงจูงใจ
- **ระบบ AI** ได้ข้อมูลดีขึ้น → แนะนำแม่นยำขึ้น → ทุกฝ่ายได้ประโยชน์

#### 5.3 Cost-Effective Operations

- **Event-driven Architecture:** AI ประมวลผลเฉพาะเมื่อมีเหตุการณ์สำคัญ (ฝนตก > 50 มม., มีรายงานน้ำท่วมใหม่) ไม่ใช่ทำงานตลอดเวลา
- **Zone-level Caching:** แคชข้อมูลระดับโซนพื้นที่ ลดการเรียก API ซ้ำ
- **Serverless First:** ใช้ Lambda + API Gateway ไม่มีค่า Server ตอนไม่มี Traffic

## ส่วนที่ 8: ระเบียบวิธีข้อมูลและตรรกะการตัดสินใจ (Data & Decision Methodology)

### 8.1 สถานะและข้อจำกัดของข้อมูลสาธิต

ข้อมูลชื่อร้าน เหตุการณ์ ตัวเลขความเสี่ยง เส้นทาง และแผนทริปในเอกสาร/Prototype นี้เป็น **ข้อมูลสังเคราะห์เพื่อการสาธิต (Synthetic Demonstration Data)** ไม่ใช่ข้อมูลเหตุการณ์จริง ไม่ควรใช้เพื่อการเดินทางจริง การแจ้งเหตุฉุกเฉิน หรือการตัดสินใจทางธุรกิจจริงโดยลำพัง ชื่อสถานที่ที่ปรากฏใช้เพื่อทำให้บริบทกรุงเทพฯ เข้าใจง่ายเท่านั้น

ในการนำไปใช้จริง แต่ละข้อมูลต้องระบุแหล่งที่มา เวลาที่อัปเดต พื้นที่ครอบคลุม ระดับความเชื่อมั่น และสิทธิการใช้งานก่อนเข้าสู่ระบบตัดสินใจ

### 8.2 Data Contract ขั้นต่ำต่อหนึ่งระเบียน

| ฟิลด์ | ตัวอย่าง | เหตุผล |
|:---|:---|:---|
| `source` | weather_provider / community_report | ตรวจสอบย้อนกลับได้ว่าข้อมูลมาจากใด |
| `observed_at` และ `ingested_at` | 2026-10-29T12:30:00+07:00 | แยกเวลาที่เกิดเหตุจากเวลาที่ระบบรับข้อมูล |
| `location` | จุดพิกัด, เขต, โซนถนน | ใช้ประเมินความใกล้เคียงโดยไม่ต้องเผยที่อยู่ละเอียดเกินจำเป็น |
| `confidence` | 0.00–1.00 | สื่อสารความไม่แน่นอนแก่โมเดลและผู้ใช้ |
| `severity` | CLEAR / SLOW / FLOODED | ทำมาตรฐานสถานะข้ามแหล่งข้อมูล |
| `verification_status` | pending / corroborated / rejected | ป้องกันรายงานซ้ำ ข้อมูลล้าสมัย หรือข้อมูลเท็จ |
| `retention_policy` | 30 days / aggregated only | ควบคุมวงจรชีวิตข้อมูลและความเป็นส่วนตัว |

### 8.3 สูตรคะแนนตัวอย่างที่ตรวจสอบได้

คะแนนต่อไปนี้เป็นกรอบต้นแบบสำหรับ Pilot ต้องปรับน้ำหนักจากผลทดสอบภาคสนาม ไม่ใช่ค่าที่อ้างว่าเป็นแบบจำลองสำเร็จรูป

```text
FloodRisk = 100 × clamp(
  0.30×RainIntensity + 0.25×WaterDepth + 0.20×RoadDisruption
  + 0.15×CommunitySignal + 0.10×DrainageConstraint, 0, 1)

BusinessImpact = FloodRisk × ExposureValue × VulnerabilityFactor
RouteScore = 0.45×Safety + 0.25×TravelReliability + 0.20×Accessibility + 0.10×Cost
```

- `RainIntensity`: ปริมาณ/ความรุนแรงฝนที่ปรับมาตราส่วนตามโซนและช่วงเวลา
- `WaterDepth`: ระดับน้ำที่ยืนยันแล้วหรือคาดการณ์ พร้อมค่าน้ำหนักตามประเภทพาหนะ
- `RoadDisruption`: สถานะถนน ความเร็ว และการปิดทาง
- `CommunitySignal`: รายงานที่ลดน้ำหนักตามอายุข้อมูล และเพิ่มน้ำหนักเมื่อยืนยันจากหลายแหล่ง
- `ExposureValue`: มูลค่าทรัพย์สินหรือรายได้ที่เจ้าของร้านยินยอมระบุ
- `VulnerabilityFactor`: ความไวของสินค้าต่อน้ำ ประเภทธุรกิจ และความพร้อมป้องกัน

### 8.4 กฎความปลอดภัยของการแนะนำ (Decision Guardrails)

| เงื่อนไข | พฤติกรรมของระบบ |
|:---|:---|
| ความเชื่อมั่นต่ำกว่าเกณฑ์ Pilot (เช่น 0.60) | ระบุว่า “ข้อมูลยังไม่เพียงพอ” และเสนอให้ตรวจสอบแหล่งทางการ แทนการฟันธง |
| จุดเส้นทางมีรายงานน้ำท่วมรุนแรงหรือถนนปิด | ไม่เสนอเส้นทางนั้นเป็นเส้นทางแนะนำ |
| รายงานชุมชนใหม่แต่ยังไม่ยืนยัน | แสดงเป็นสัญญาณเบื้องต้น แยกจากข้อมูลยืนยันแล้ว |
| มีเหตุฉุกเฉินต่อชีวิต | แสดงช่องทางติดต่อหน่วยงานฉุกเฉิน/คำแนะนำทางการ ไม่แทนที่การช่วยเหลือฉุกเฉิน |
| คำแนะนำธุรกิจอาจก่อค่าใช้จ่ายสูง | แสดงเหตุผลและทางเลือกต้นทุนต่ำก่อนเสมอ |

## ส่วนที่ 9: แผนดำเนินงาน Bangkok Pilot (Pilot Operating Plan)

### 9.1 เป้าหมายการทดสอบ 12 สัปดาห์

| ระยะเวลา | งานหลัก | ผลส่งมอบ/เกณฑ์ผ่าน |
|:---|:---|:---|
| สัปดาห์ 1–2 | คัดเลือกพื้นที่, ทำ Data Inventory, สัมภาษณ์ SME และกำหนดเกณฑ์ความเสี่ยงร่วมกัน | Pilot Charter, รายการข้อมูล, แบบฟอร์มความยินยอม |
| สัปดาห์ 3–4 | เชื่อมข้อมูลแบบ Sandbox, สร้าง SME Profile และชุด Action Template | Data Contract ผ่านการทดสอบ, Template อย่างน้อย 5 ประเภทธุรกิจ |
| สัปดาห์ 5–6 | ทดสอบระบบภายใน, จำลองเหตุการณ์, ตรวจความเข้าใจข้อความภาษาไทย | UAT รอบ 1, บันทึกข้อผิดพลาดและการแก้ไข |
| สัปดาห์ 7–10 | เปิดใช้แบบจำกัดกลุ่ม, เก็บ telemetry และ feedback รายสัปดาห์ | รายงาน adoption, ความตรงเวลา, ความพึงพอใจ |
| สัปดาห์ 11–12 | ประเมินผล, ทบทวนความเสี่ยง, ตัดสินใจขยาย/ปรับ/หยุด | Pilot Evaluation Report และแผนระยะถัดไป |

### 9.2 ตัวอย่างเกณฑ์คัดเลือกพื้นที่และผู้เข้าร่วม

- พื้นที่มีบริบทความเสี่ยงน้ำขัง/การเดินทางชัดเจน และมีผู้ประสานงานชุมชน
- ผู้ประกอบการสมัครใจเข้าร่วมและยอมรับว่าเครื่องมือเป็น decision support
- มีความหลากหลายของประเภทธุรกิจ เพื่อทดสอบ Action Template ได้จริง
- มีช่องทางรับ feedback ที่เข้าถึงง่าย เช่น LINE OA, โทรศัพท์ หรือแบบฟอร์มสั้น
- หลีกเลี่ยงการเก็บข้อมูลพิกัดบ้านพักหรือข้อมูลอ่อนไหวที่ไม่จำเป็นต่อการให้บริการ

### 9.3 RACI ระดับ Pilot

| งาน | ทีมแพลตฟอร์ม | ผู้ประสานงานพื้นที่ | SME/ผู้ใช้ | หน่วยงานข้อมูล |
|:---|:---:|:---:|:---:|:---:|
| คุณภาพข้อมูลและการเฝ้าระวังระบบ | R/A | C | I | C |
| ยืนยันบริบทพื้นที่และช่องทางสื่อสาร | C | R/A | C | I |
| ทำ/ยอมรับ Action Plan | C | C | R/A | I |
| อนุมัติสิทธิและการใช้ข้อมูลต้นทาง | I | C | I | R/A |
| ประเมินผล Pilot | R | C | C | C |

R = รับผิดชอบทำงาน, A = ผู้รับผิดชอบสูงสุด, C = ให้คำปรึกษา, I = รับทราบ

## ส่วนที่ 10: การวัดผล การทดลอง และเกณฑ์ความสำเร็จ (Measurement & Evaluation)

### 10.1 KPI ที่แยก “ผลใช้ระบบ” ออกจาก “ผลกระทบ”

| มิติ | ตัวชี้วัด | วิธีวัด | เป้าหมาย Pilot ที่เสนอ |
|:---|:---|:---|:---|
| Adoption | อัตราผู้ได้รับแจ้งเตือนที่เปิดดู | unique opens / notifications delivered | ≥ 60% |
| Actionability | อัตราที่ผู้ใช้ทำ Action อย่างน้อย 1 ข้อ | participating businesses with completed action / alerted businesses | ≥ 50% |
| Timeliness | เวลาจากสัญญาณถึงการแจ้งเตือน | alert timestamp − event ingestion timestamp | median < 10 นาที สำหรับข้อมูลที่พร้อมใช้ |
| Quality | สัดส่วนคำแนะนำที่ผู้ใช้ให้คะแนน “เกี่ยวข้อง” | relevant ratings / total ratings | ≥ 75% |
| Routing | อัตราเส้นทางแนะนำที่ผู้ใช้ยอมรับ | accepted route / route recommendations viewed | เก็บเป็น baseline ก่อนตั้งเป้า |
| Equity | สัดส่วน SME รายย่อยที่ได้รับการแสดงผล | micro-SME served / total SMEs served | รายงานแยกตามพื้นที่และประเภทธุรกิจ |
| Safety | จำนวนข้อร้องเรียน/เหตุแนะนำผิดร้ายแรง | incident log ที่ตรวจสอบแล้ว | 0 เหตุร้ายแรง; ทบทวนทุกเหตุการณ์ |

### 10.2 วิธีประเมินผลที่ไม่กล่าวเกินจริง

1. เก็บ baseline ก่อนเปิดใช้: วิธีรับข่าวสารเดิม เวลาตัดสินใจ และ Action ที่เคยทำ
2. ทุก Alert ให้ผู้ใช้ตอบแบบสั้น: “ข้อมูลทันหรือไม่”, “ทำอะไรตามหรือไม่”, “คำแนะนำใดใช้ไม่ได้”
3. เปรียบเทียบก่อน–หลังในร้านเดิมอย่างระมัดระวัง และบันทึกปัจจัยภายนอก เช่น ความรุนแรงของฝนหรือวันหยุด
4. รายงานผลเป็นช่วงความเชื่อมั่นและจำนวนตัวอย่างเมื่อมีข้อมูลเพียงพอ ไม่สรุปเหตุและผลจากกลุ่มตัวอย่างเล็ก
5. ทบทวนผลกับผู้ใช้และผู้ประสานงานพื้นที่ก่อนตัดสินใจขยายผล

### 10.3 นิยามเหตุการณ์และการตรวจสอบ

| เหตุการณ์ | นิยามที่บันทึก | หลักฐานขั้นต่ำ |
|:---|:---|:---|
| Alert delivered | ระบบส่งข้อความสำเร็จไปยังช่องทางที่ลงทะเบียน | delivery receipt / API log |
| Action completed | ผู้ใช้ยืนยันว่าดำเนินการแล้ว | user acknowledgement พร้อมเวลา |
| Route disruption | เส้นทางไม่สามารถใช้งานได้ตามปกติ | ข้อมูลถนนอย่างน้อย 1 แหล่ง หรือรายงาน corroborated |
| Material incident | คำแนะนำอาจสร้างความเสี่ยงหรือความเสียหายสำคัญ | incident ticket, owner, เวลาแก้ไข และ postmortem |

## ส่วนที่ 11: ความเป็นส่วนตัว ความปลอดภัย และการกำกับดูแล (Privacy, Safety & Governance)

### 11.1 หลักการคุ้มครองข้อมูลตั้งแต่การออกแบบ

- เก็บเท่าที่จำเป็น: ใช้โซนพื้นที่แทนพิกัดละเอียดเมื่อการตัดสินใจไม่ต้องใช้จุดจริง
- แยกข้อมูลระบุตัวบุคคลออกจากข้อมูลวิเคราะห์ และกำหนดสิทธิ์เข้าถึงตามบทบาท
- ขอความยินยอมที่อ่านเข้าใจง่าย สำหรับการลงทะเบียนร้าน การรับแจ้งเตือน และการส่งรายงานชุมชน
- ให้ผู้ใช้แก้ไข ถอนความยินยอม หรือขอลบข้อมูลของตนได้ตามนโยบายที่ประกาศ
- ใช้ข้อมูลรวม/ลดการระบุตัวตนสำหรับรายงานเชิงสถิติและการพัฒนาโมเดล

### 11.2 Threat Model เบื้องต้นและมาตรการลดความเสี่ยง

| ความเสี่ยง | ผลกระทบ | การควบคุมที่เสนอ |
|:---|:---|:---|
| รายงานเท็จหรือ spam | เส้นทาง/Alert คลาดเคลื่อน | rate limit, reputation score, ตรวจหลายแหล่ง, ช่องทางรายงานปัญหา |
| ข้อมูลล้าสมัย | ผู้ใช้ตัดสินใจจากสถานะเก่า | time-to-live, ป้ายเวลาเด่นชัด, ลดน้ำหนักข้อมูลตามอายุ |
| การเข้าถึงโปรไฟล์ SME โดยมิชอบ | ความเป็นส่วนตัว/ความเสียหายเชิงธุรกิจ | RBAC, encryption in transit/at rest, audit log |
| LLM สร้างคำแนะนำเกินหลักฐาน | คำแนะนำไม่น่าเชื่อถือ | grounded retrieval, structured templates, confidence threshold, human review สำหรับข้อความสำคัญ |
| การพึ่งพาระบบมากเกินไป | ความเสี่ยงต่อความปลอดภัย | แสดงข้อจำกัด, ลิงก์แหล่งข้อมูลทางการ, ไม่อ้างว่าแทนหน่วยงานฉุกเฉิน |

### 11.3 Human-in-the-loop และช่องทางอุทธรณ์

คำแนะนำระดับความเสี่ยงสูงต้องมีเส้นทางให้เจ้าหน้าที่หรือผู้ประสานงานตรวจทานก่อนส่งแบบวงกว้าง ผู้ใช้สามารถกด “ข้อมูลไม่ถูกต้อง” และระบุเหตุผลได้ ทุกกรณีที่มีผลต่อความปลอดภัยจะถูกบันทึกเป็น incident และทบทวนสาเหตุ ร่องรอยข้อมูล และการแก้ไขก่อนนำกฎกลับมาใช้

## ส่วนที่ 12: แผนความเสี่ยง ความต่อเนื่อง และงบประมาณสมมติฐาน (Risk, Continuity & Assumptions)

### 12.1 Risk Register สำหรับการเริ่ม Pilot

| ความเสี่ยง | โอกาส | ผลกระทบ | สัญญาณเตือน | วิธีรับมือ | เจ้าของ |
|:---|:---:|:---:|:---|:---|:---|
| แหล่งข้อมูลหยุดให้บริการ | กลาง | สูง | freshness เกิน SLA | ใช้ cache ล่าสุดพร้อมป้ายเวลา, fallback source, ลดความสามารถบางส่วนอย่างปลอดภัย | Tech Lead |
| ความแม่นยำต่างกันตามเขต | สูง | กลาง | feedback ลบกระจุกตัว | calibration รายโซน, เพิ่มการตรวจภาคสนาม, ไม่แสดงคะแนนเทียม | Data Lead |
| ผู้ใช้ไม่ทำตาม Action | กลาง | กลาง | completion ต่ำ | ลดจำนวนขั้นตอน, ปรับภาษา/เวลา, สัมภาษณ์หาสาเหตุ | Product Lead |
| ข้อมูลชุมชนถูกบิดเบือน | กลาง | สูง | รายงานพุ่งผิดปกติ | deduplication, reputation, moderation queue | Operations Lead |
| เหตุการณ์รุนแรงเกินขอบเขตระบบ | ต่ำ | สูงมาก | สัญญาณเตือนภัยทางการ | ใช้ข้อความมาตรฐาน, ชี้ไปช่องทางฉุกเฉิน, ระงับคำแนะนำอัตโนมัติที่ไม่เหมาะสม | Incident Commander |

### 12.2 Service Degradation Playbook

1. **ข้อมูลบางแหล่งล่ม:** แสดงเวลาปรับปรุงล่าสุดของแต่ละชั้นข้อมูล ปิดคำแนะนำที่ต้องใช้แหล่งนั้น และคงเฉพาะข้อมูลที่ยืนยันได้
2. **โมเดล/LLM ใช้ไม่ได้:** เปลี่ยนเป็นกฎ Action Template แบบกำหนดไว้ล่วงหน้า พร้อมระบุว่าเป็นคำแนะนำทั่วไป
3. **รายงานชุมชนพุ่งผิดปกติ:** จำกัดการเผยแพร่สาธารณะ ส่งเข้าคิวตรวจ และไม่เพิ่มคะแนนความเสี่ยงจนกว่าจะ corroborated
4. **มีรายงานความเสียหายจากคำแนะนำ:** ระงับกฎหรือเส้นทางที่เกี่ยวข้อง เปิด incident, แจ้งผู้ใช้ที่อาจได้รับผลกระทบ และทำ postmortem

### 12.3 สมมติฐานงบประมาณสำหรับการวางแผน ไม่ใช่ใบเสนอราคา

| หมวด | สมมติฐานต้นทุน | ตัวแปรที่ทำให้เปลี่ยนแปลง |
|:---|:---|:---|
| พัฒนาระบบ MVP | ทีมผลิตภัณฑ์ขนาดเล็ก 3–5 บทบาทในช่วงสร้างและทดสอบ | ขอบเขต mobile app, ระบบยืนยันตัวตน, การเชื่อมข้อมูลจริง |
| Cloud/AI | ขึ้นกับจำนวน Alert, API call, ปริมาณ retrieval และ retention | จำนวนผู้ใช้, event volume, provider pricing |
| งานพื้นที่ | อบรมผู้เข้าร่วม, support, เก็บ feedback และตรวจคุณภาพ | จำนวนเขต/SME, ความถี่ลงพื้นที่ |
| Governance | นโยบายข้อมูล, review ด้านความปลอดภัย และ incident drill | ประเภทข้อมูลและข้อกำหนดคู่ค้า |

ก่อนใช้งบจริง ต้องจัดทำ BOQ, SLA แหล่งข้อมูล, ข้อกำหนดความปลอดภัย และแผนจัดซื้อร่วมกับหน่วยงานเจ้าของโครงการ

| ชิ้นส่งมอบ | เกณฑ์ตรวจรับ | หลักฐาน |

| Action Template | ครอบคลุมประเภทธุรกิจนำร่องและมีผู้ใช้ตรวจความเข้าใจ | บันทึก workshop/UAT และเวอร์ชัน template |

### Definition of Done สำหรับการขยายจาก Pilot

- ผ่านเกณฑ์ความปลอดภัยและไม่มี incident ร้ายแรงที่ยังไม่มีมาตรการป้องกัน
- มีหลักฐานว่า Alert และ Action มีคุณค่าแก่ผู้ใช้เป้าหมาย ไม่ใช่เพียงการเปิดดูหน้า Dashboard
- แหล่งข้อมูลสำคัญมี SLA หรือแผน fallback ที่ทดสอบแล้ว
- มีเจ้าของกระบวนการ support, moderation และ incident response ชัดเจน
- ผลกระทบต่อกลุ่มผู้ใช้รายย่อยได้รับการตรวจสอบ ไม่เกิดการกระจุกประโยชน์เฉพาะร้าน/พื้นที่ที่มีข้อมูลมาก

## ส่วนที่ 14: บทสรุปสำหรับกรรมการ (Closing Statement)

Local Intelligence Platform เสนอวิธีเปลี่ยนข้อมูลเมืองที่กระจัดกระจายให้เป็นการตัดสินใจที่ทำได้จริงในระดับคน ร้านค้า และเส้นทาง ผ่านวงจรเดียวกันคือ **รับรู้ความเสี่ยง → เข้าใจผลกระทบ → เลือกการกระทำ → เรียนรู้จากผลลัพธ์**

Prototype แสดงประสบการณ์ผู้ใช้ที่จับต้องได้สำหรับ 3 Track ขณะที่แผน Pilot ระบุขอบเขต ข้อมูล วิธีวัดผล การคุ้มครองข้อมูล และกลไกรับมือความเสี่ยงอย่างชัดเจน สิ่งที่เอกสารนี้อ้างว่า “สาธิตได้แล้ว” คือประสบการณ์บนข้อมูลสังเคราะห์; สิ่งที่เสนอให้ร่วมกันพิสูจน์ต่อคือคุณค่าและความปลอดภัยบนข้อมูลจริงภายใต้การกำกับดูแลที่เหมาะสม

> **Local Intelligence Platform: จากข้อมูลเมือง สู่การตัดสินใจที่ทันท่วงที ปลอดภัย และเป็นธรรมต่อเศรษฐกิจท้องถิ่น**
